| 표기 | 뜻 |
| --- | --- |

## 1. 앱 한 줄 소개

사고 직후 운전자가 차 안 화면에서 먼저 안전을 확인하고, 필요하면 직접 119에 연결하고, 사고 내용을 남겨 보험사에 보낼 범위까지 스스로 정리하도록 돕는 Pleos 차량용 사고 대응 앱이다.

## 2. 기획 배경

**주목한 순간.** 경미한 접촉 사고 직후 운전자는 놀란 상태로 여러 일을 동시에 판단해야 한다. 다친 사람이 있는지, 차를 세워 둔 곳이 위험한지, 119에 연락해야 하는지, 무엇을 찍고 적어야 하는지, 보험사에 무엇을 보내야 하는지를 정해진 순서 없이 떠올려야 한다. 이때 휴대폰은 바닥에 떨어져 있거나 통화에 쓰이고 있을 수 있다. 반면 차량 화면은 운전석 바로 앞에 고정돼 있고 차량 상태를 알고 있다.

**기존 방식의 빈틈.** 사고 대응 정보는 보험사 앱, 휴대폰 메모, 카메라, 전화로 흩어져 있다. 대부분 사고가 정리된 뒤 휴대폰에서 양식을 채우는 흐름이다. 그 결과 다음 두 문제가 생긴다고 판단했다.

- 기록과 접수가 안전 확인보다 앞에 놓인다. 위험한 도로 위에서 사진부터 찍게 만들 수 있다.
- 사용자가 한 행동과 외부의 실제 결과가 섞인다. "전화를 눌렀다"와 "구조 요청이 접수됐다"를, "자료를 보냈다"와 "보험 접수가 됐다"를 구분하기 어렵다.

**해결이 필요한 이유.** 사고 직후의 판단 실수는 2차 사고나 기록 누락으로 이어질 수 있다. 차량은 사고 순간 운전자와 가장 가까운 화면이므로 안전 확인을 먼저, 기록은 나중에 할 수 있게 순서를 잡아 주는 역할에 적합하다.

**관찰과 가설의 구분.** 위 문제 인식은 팀의 시나리오 검토와 공개 안전 지침을 바탕으로 한 가설이다. 사용자 조사나 사고 통계로 검증하지 않았다. 출처를 확인한 통계가 없으므로 사고 건수·피해 규모 같은 수치를 쓰지 않았다. 실제 운전자 대상 이해도 평가는 아직 실시하지 않았고 개발 계획에 포함했다.

## 3. 앱 주요 기능 및 차량 특화 요소

### 3.1 핵심 기능

| 기능 | 해결하는 문제 | 상태 |
| --- | --- | --- |
| **상황 먼저 확인** | 첫 화면은 "다친 사람이나 위험한 상황이 있나요?"를 묻는다. 답에 따라 119 연결, 대피 안내, 기록 순서가 달라진다. 모든 사고를 같은 순서로 밀어 넣지 않는다 | [구현] |
| **119는 운전자가 누를 때만** | 119 칸은 운전자가 위험을 알리거나 에어백 전개 신호가 있을 때만 나타난다. `119에 연결`을 누르면 Android 전화 앱에 `119`를 채워 열고, 실제 발신은 운전자가 누른다. 앱이 자동으로 전화하거나 신고를 접수하지 않는다 | [구현] 화면·다이얼 연결. 실제 통화 연결 결과는 앱이 알 수 없음 |
| **에어백 전개 신호 반영** | Pleos Vehicle SDK의 좌석별 에어백 전개 조회·변경 알림을 읽는다. 전개 신호가 오면 "에어백이 펼쳐졌어요"로 시작하고 119 칸을 보여 준다. 신호를 읽을 수 없으면 "신호 확인 불가"로 표시하고 "사고 없음"으로 바꾸지 않는다 | [구현] SDK 연결·권한·지원 여부 처리. 에뮬레이터 값은 `시뮬레이션`으로 표시. 실차 전개 신호 수신은 미검증 |
| **대피 체크리스트** | 비상등 켜기, 트렁크 열기, 대피할 곳 찾기, 휴대폰 챙기기를 운전자가 직접 확인한다. 시간이 지났다고 완료로 바꾸지 않는다 | [구현] 운전자 확인. 차량 신호로 자동 확인하는 기능은 [계획] |
| **차 화면에서 기록** | 기록 단계는 "어떻게 부딪혔나요?"를 묻는다. `말로 남기기`에서 내용을 직접 입력해 저장하거나, 차량 마이크로 녹음한다. 저장한 기록은 차량 앱 안에 보관된다 | [구현] 직접 입력·저장은 에뮬레이터에서 동작. 녹음에는 마이크가 필요하며, 에뮬레이터는 기본 설정에서 호스트 마이크를 넘기지 않아 시연 영상에서 보여 줌 |
| **휴대폰으로 이어 기록** | 차량 화면의 QR을 휴대폰으로 읽으면 같은 사고 기록이 휴대폰에서 열린다. 휴대폰에 뜬 6자리 확인 숫자를 차량 화면에서 확인하고 운전자가 직접 승인해야 연결된다. 휴대폰에서 사진·음성·진술·경위서를 남기면 차량 화면의 기록 칸에 개수와 작성 상태가 갱신된다 | [연결 시연]. 제출 APK에서는 `휴대폰으로 남기기`와 연결 화면이 나타나지 않음 |
| **기록 보류** | 기록은 선택이다. 차량의 기록 단계에서 `나중에 기록할게요`를 누르면 기록 없이 이후 할 일로 넘어간다. 휴대폰에서는 `잠시 쉬기`로 멈추고, 다시 시작할 때 주변 상태를 한 번 더 확인한다 | [구현] 차량 화면. 휴대폰 쪽은 [연결 시연] |
| **새 위험이 생기면 기록보다 안전 먼저** | 기록 중 새 위험 정보가 들어오면 차량 안내 칸이 "주변을 다시 살펴보세요"로 바뀐다. 운전자가 `주변을 확인했어요`를 누르면 작성하던 기록과 커서 위치 그대로 돌아간다 | [구현] 화면 전환과 복귀. 제출 APK의 위험 입력은 `시연` 버튼([시연]). 휴대폰 `새 위험이 있어요`가 차량 화면을 바꾸는 경로는 현재 빌드에서 미검증. 차량 센서로 새 위험을 감지하는 기능은 [계획] |
| **보낼 내용을 직접 고르고 승인** | 받는 곳(보험사, 차량 지원, 상대방 공유)과 보낼 자료를 운전자가 고르고 미리 본 뒤 승인한다. `나중에 결정`과 `전송하지 않기`도 정상 경로이며 기록은 유지된다 | [구현] 선택·미리보기·승인 기록 |
| **보험사 전달** | 실제 보험사 API는 연결돼 있지 않다. 차량 화면의 보험사 전송·접수 상태는 `시연` 표시와 함께 흐름을 보여 주는 용도다. 휴대폰을 연결하면 승인한 범위만 담은 "내 기록 사본"(JSON 파일과 원본 사진·음성)을 내려받아 운전자가 직접 보험사에 전달할 수 있다 | [시연] 보험사 전송·접수 결과. 사본 내려받기는 [연결 시연] |
| **차분한 음성 안내** | 장면마다 짧은 한국어 안내 음성이 차량 스피커로 나온다. 화면을 오래 볼 수 없는 상황을 고려했다. 별도의 음성 버튼 없이 장면에 맞춰 재생된다 | [구현] 미리 생성한 음성 파일. Pleos TextToSpeech SDK 전환은 [계획] |

### 3.2 휴대폰만 쓸 때와 다른 차량 특화 요소

1. **사고 순간 가장 가까운 화면.** 휴대폰을 찾거나 잠금을 풀지 않아도 운전석 앞 화면에서 바로 상황 확인을 시작한다.
2. **차가 아는 정보를 쓴다.** 에어백 전개 신호를 Vehicle SDK로 읽어 첫 질문과 119 칸 노출에 반영한다. 차가 모르는 값은 "미확인"으로 둔다.
3. **차와 휴대폰의 역할 분담.** 차량은 상황·차량 상태·안내·진행 현황을 보여 주고, 차 안에서 말로 기록한다. 휴대폰은 차 밖에서 촬영·진술·경위서 수정·사본 준비를 맡는다. 두 기기는 같은 사고 기록 하나를 공유한다. 휴대폰 연결은 [연결 시연]이며 제출 APK는 차량 단독으로 동작한다.
4. **Pleos 화면 구조에 맞춘 배치.** 시스템 영역(Driving view, 상태 표시줄, GNB)을 침범하지 않고 앱 창(1682×1210) 안에서만 동작한다. 화면 분할 시 세로 앱 창(약 841×1210)에서도 같은 흐름이 보인다.
5. **운전 중 조작을 줄이는 화면.** 다음 단계로 가는 방법은 각 칸 안의 행동 버튼뿐이다. 버튼 높이는 48px 이상이다. 한 장면의 주 행동은 하나로 제한했다.

### 3.3 화면 구성

앱 창을 세 열로 나눈다. 칸 사이 경계는 비스듬한 보로노이(Voronoi) 분할선이며 단계가 바뀌면 칸의 크기만 부드럽게 바뀐다. 칸의 좌우 순서는 바뀌지 않는다.

| 위치 | 칸 | 내용 |
| --- | --- | --- |
| 왼쪽 위 | 주변 상황 | 도로, 내 차와 상대 차의 윤곽, 충격 위치, 되돌려 보기 |
| 왼쪽 아래 | 차량 상태 | 충격 방향, 비상등, 트렁크, 차량 이동 여부와 요청 상태(구호, 차량 지원, 보험사). 주의가 필요할 때만 따뜻한 색으로 바뀜 |
| 가운데 | 지금 할 일 | 질문, 체크리스트, 행동 버튼. 긴급 상황에서만 위쪽에 119 칸이 나타남 |
| 오른쪽 | 사고 내용 기록 중 | 남긴 기록 개수, 직접 남긴 내용. 연결 시연 빌드에서는 휴대폰 연결 상태도 표시 |

시연용 사례의 차량 상태·위치 값은 화면에 `시연`·`예시 자료`로 표시한다. 블랙박스 영상, 외부 카메라, 경위서 자동 작성은 화면에 넣지 않았다. 해당 데이터 접근 권한을 확보하지 못했기 때문이다.

## 4. 주요 사용 시나리오

### 4.1 대표 시나리오: 일반도로의 경미한 접촉 사고

**누가.** Pleos Connect 차량을 운전하는 개인 운전자. 사고 직후 응답과 조작이 가능하다.

**상황.** 일반도로 2차로를 주행하다 우측 차량과 가볍게 접촉했다. 다친 사람은 없다.

| 순서 | 차량 화면 | 운전자 행동 | 다음 조건 |
| --- | --- | --- | --- |
| 1 | "다친 사람이나 위험한 상황이 있나요?" 안내 음성과 함께 질문이 나온다. 119 칸은 아직 없다 | `급한 위험은 없어요`를 누른다 | 위험이 없다는 운전자 답 |
| 2 | 대피 체크리스트가 나온다. 비상등, 트렁크, 대피할 곳, 휴대폰 | 해당 항목을 직접 체크하고 `안전한 곳에 있어요`를 누른다 | 운전자의 안전 위치 확인 |
| 3 | "안전한 곳에 머물러 주세요. 이제 기억나는 내용을 남길 수 있어요." | `기록 시작`을 누른다 | 기록할 수 있다는 운전자 판단 |
| 4 | 가운데 칸이 "어떻게 부딪혔나요?"를 묻고 오른쪽 기록 칸이 넓어진다 | `말로 남기기`에서 직접 입력하거나 녹음해 저장한다. 지금 어려우면 `나중에 기록할게요`를 누른다 | 실제로 저장된 기록이 있어야 `남긴 내용 확인`이 활성화됨 |
| 5 | (연결 시연) `휴대폰으로 남기기`에 QR이 나오고, 휴대폰 승인 뒤 기록 칸에 사진·음성·진술·경위서 상태가 갱신된다 | 휴대폰으로 QR을 읽고 6자리 숫자를 확인해 차량에서 승인한 뒤, 차 밖에서 사진과 진술을 남긴다 | 차량에서의 직접 승인. 코드는 5분 뒤 만료되며 새 코드를 받을 수 있음 |
| 6 | "보험사에 보낼 내용을 확인하세요" | 받는 곳과 보낼 자료를 고르고 미리 본 뒤 승인한다. 또는 `나중에 결정`, `전송하지 않기`를 고른다 | 운전자의 명시적 승인 |
| 7 | 보낸 기록과 남은 일을 보여 준다. 보험사 접수는 "미확인"으로 남는다 | 실제 보험사 접수는 운전자가 앱 밖에서 진행한다. (연결 시연) 휴대폰에서 승인한 범위의 사본을 내려받아 전달한다 | 전송·접수 결과는 `시연` 입력으로만 바뀜 |

### 4.2 핵심 분기

- **긴급 상황.** 1단계에서 `다친 사람이 있거나 위험해요`를 누르거나 에어백 전개 신호가 들어오면 가운데 열 위쪽에 119 칸이 나타난다. 안내는 "다친 사람은 억지로 움직이지 마세요. 불이나 연기가 보이면 차에서 멀리 떨어지세요."다. 운전자가 `119에 연결`을 눌러야 전화 앱이 열린다. 통화 중에도 대피 안내와 기록은 별개로 유지된다. 구호 접수 여부는 앱이 확인할 수 없으므로 "구호 접수 미확인"으로 둔다.
- **기록하기 어렵거나 원하지 않을 때.** 기록은 필수가 아니다. 기록 단계 안내는 "어떻게 부딪혔나요? 말로 하거나 사진을 찍어 두세요. 지금 어려우면 나중에 해도 돼요."다. 차량에서 `나중에 기록할게요`를 누르면 이후 할 일로 넘어간다. (연결 시연) 휴대폰에서는 `잠시 쉬기`, `기록 없이 이후 할 일 보기`를 고를 수 있고, 다시 이어갈 때 주변 상태를 한 번 더 확인한다. 빈 기록을 전송 성공으로 만들지 않는다.
- **새 위험이 생겼을 때.** 기록 중 새 위험 정보가 들어오면 차량 안내가 "주변을 다시 살펴보세요"로 바뀌고, 차량 상태 칸에 "새로운 위험 감지"가 표시된다. `주변을 확인했어요`를 누르면 작성하던 기록 그대로 돌아간다. 위험하면 `다친 사람이 있거나 위험해요`로 119 칸에 바로 갈 수 있다. 제출 APK에서는 `시연` 버튼으로 위험 정보를 넣는다. 휴대폰에서 알린 위험이 차량 화면을 바꾸는 경로는 현재 빌드에서 검증하지 않았다.
- **보험 전송을 거절하거나 미룰 때.** `나중에 결정`과 `전송하지 않기`는 정상 경로다. 남긴 기록은 유지되고 언제든 다시 검토할 수 있다.
- **휴대폰 연결이 끊겼을 때 (연결 시연).** 마지막으로 저장된 기록은 서버에 남는다. 차량 화면은 "휴대폰 응답 없음"을 보여 주고 `새로 연결하기`로 다시 연결할 수 있다.

## 5. 개발 계획

### 5.1 현재 구현 범위 (1차 접수 시점)

**구조.** 제출 APK는 서버 없이 동작하는 차량 단독 앱이다. 사고 기록은 차량 앱 안에 저장한다. 휴대폰 이어받기는 사고 기록 서버 주소를 넣어 빌드한 APK에서만 켜진다. 시연 영상과 2차 PT에서는 개발 장비에서 실행한 서버를 Cloudflare 터널의 HTTPS 주소로 열어 연결한다.

| 구성 | 역할 | 기술 | 제출 APK |
| --- | --- | --- | --- |
| Pleos 차량 앱 | Native 계층이 Pleos SDK, 119 다이얼, 차량 신호 전달을 맡는다. 화면은 APK에 함께 넣은 웹 UI를 WebView로 띄운다 | Kotlin, Android API 28 이상(minSdk 28), Pleos Vehicle SDK 2.3.2, AndroidX WebKit | 포함 |
| 차량 화면 UI | 세 열 보로노이 화면, 단계 흐름, 음성 안내, 차 안 기록 | React, TypeScript, Vite. 인터넷에서 불러오지 않고 APK 안의 파일만 사용 | 포함 |
| 휴대폰 화면 | QR로 열리는 모바일 웹. 사진·음성·진술·경위서 작성, 공유 범위 승인, 사본 내려받기 | 같은 React 코드의 `/phone` 화면 | 연결 시연 |
| 사고 기록 서버 | 사고 기록 저장, 차량 인증, QR 연결과 확인 숫자 승인, 차량 진행 현황, 파일 업로드 검사 | Bun, SQLite, HTTPS 전용 | 연결 시연 |

**Pleos 보안 가이드 적용.** WebView는 `WebViewAssetLoader`로 APK 안의 파일만 HTTPS 형식 주소(`https://appassets.androidplatform.net/assets/web/`)로 연다. 파일 직접 접근(`allowFileAccess`, `allowContentAccess`)을 끄고, 다른 주소로의 이동을 막는다. JavaScript 연결 통로(`window.ChabunNative`)는 호스트 정보, 휴대폰 연결, 119 다이얼, 차량 신호 전달만 노출한다. 서버 주소 없이 빌드하면 휴대폰 연결 기능은 꺼진다. 연결 빌드의 차량 인증 정보는 Android Keystore의 AES-GCM 키로 암호화해 Native 저장소에만 두고, 웹 저장소나 URL에 넣지 않는다. release 빌드는 별도 키로 서명한다.

**서버 보안 (연결 시연).** 차량은 `Authorization: Bearer` 차량 인증 정보로, 휴대폰은 `__Host-` 쿠키 세션으로 접근한다. QR 연결 코드는 5분 뒤 만료되고, 휴대폰 연결은 차량에서 6자리 확인 숫자를 보고 승인해야 완료된다. 모든 변경 요청은 기록 버전(`expectedRevision`)과 요청 ID(`mutationId`)를 함께 보내 중복 전송과 동시 수정 충돌을 서버에서 구분한다.

**SDK·API 사용 현황.**

| SDK·API | 사용 내용 | 상태 |
| --- | --- | --- |

## 6. 기대효과 및 발전 가능성

### 6.1 사용자에게 주는 가치

- **안전이 먼저인 순서.** 기록과 보험 처리보다 부상·위험 확인과 대피가 먼저 나온다. 기록은 언제든 미룰 수 있다.
- **헷갈리지 않는 상태.** "운전자가 누른 것"과 "외부에서 확인된 것"을 나눠 보여 준다. 예를 들어 보험사 전송 뒤에도 접수 확인 전까지는 "보험사 접수 미확인"으로 둔다.
- **두 번 쓰지 않는 기록.** 차와 휴대폰이 같은 사고 기록을 공유하므로 차에서 시작한 기록을 휴대폰에서 이어 쓰고, 승인한 범위만 사본으로 정리한다. 이 연결은 시연 영상과 2차 PT에서 보여 준다.

### 6.2 타깃 고객

| 구분 | 고객 | 필요 |
| --- | --- | --- |
| 1차 사용자 | Pleos Connect 탑재 차량의 개인 운전자, 특히 사고 경험이 적은 운전자 | 사고 직후 무엇부터 할지 안내 |
| 확장 사용자 | 렌터카·카셰어링 이용자 | 익숙하지 않은 차에서의 사고 대응, 운영사에 보낼 기록 정리 |

### 6.3 MAU와 Retention의 정의 [가정]

사고 대응 앱은 매일 쓰는 앱이 아니다. 일상 MAU를 성과 지표로 쓰면 실제 가치를 잘못 보여 준다. 그래서 지표를 다음처럼 정의한다.

- **사고 처리 MAU** = 한 달 동안 앱에서 사고 기록을 1건 이상 시작한 차량 수.
  추정식: `MAU = N × r × a`
  - `N`: 앱을 설치했거나 기본 탑재된 Pleos 차량 수
  - `r`: 차량 1대가 한 달에 사고를 겪을 확률
  - `a`: 사고 차량 중 앱을 여는 비율 (기본 탑재·에어백 신호 연동이면 높아질 것으로 가정)
  - 세 값 모두 출처를 확인한 수치가 없다. `N`은 배포 계약, `r`은 보험사 또는 공공 통계의 출처 확인, `a`는 시범 운영 측정으로 정해야 한다. 예를 들어 `N = 10,000대`, `r = 0.5%`, `a = 50%`라고 **가정**하면 MAU는 25대다. 이 값은 계산 방법을 보여 주는 가정값이며 예측이 아니다.
- **사고 처리 Retention** = 사고 기록을 시작한 사람 중 7일 안에 다시 들어와 기록 확인이나 사본 준비를 마친 비율. 사고 후 후속 처리를 실제로 끝냈는지를 본다.
- **평상시 재방문** = 사고 없는 기간에 대비 정보(보험사 연락처 등록, 체크리스트 확인)를 확인한 사용자 비율. [계획] 기능을 전제로 한 지표다.

### 6.4 측정할 효과 [계획]

| 효과 | 측정 방법 |
| --- | --- |
| 안전 확인이 기록보다 먼저 이뤄지는가 | 기록 시작 전 위험 질문 답변과 대피 체크 완료 비율 |
| 기록이 실제로 남는가 | 사고 기록 중 사진·진술·경위서가 1개 이상 있는 비율 |

| 다음 행동을 이해하는가 | 운전자 이해도 평가에서 안내 없이 다음 행동을 고른 비율 |

### 6.5 서비스 확대 계획

1. **차량 신호 확대.** 공개 Vehicle SDK의 다른 상태(비상등, 문, 기어)를 capability 확인 후 연결한다.
2. **사고 감지 보강.** 운행 전 휴대폰 연결을 통한 충돌 의심 감지와, 계약 후 Fleet 충돌 상태 수신을 연구한다.
3. **보험사 제휴.** 운전자가 승인한 사본을 보험사 접수 채널로 보내고 접수 결과를 앱에 반영한다. 지금의 사본에는 승인 시각과 운전자가 고른 관찰·진술·사진·음성·경위서만 담긴다.
4. **렌터카·법인 차량.** 운영사 정책(연락처, 필수 기록 항목)을 사고 기록에 붙여 운영사 접수까지 이어 준다.
5. **수익 모델 [가정].** 차량 플랫폼 기본 탑재 계약, 보험사 접수 연동 수수료, 렌터카·법인 차량 운영사 대상 B2B 이용료를 검토한다. 어느 모델도 협의하거나 검증하지 않았다.
