# 검증 기준과 평가 방법

## 자동 검사

- 세 scenario와 모든 장면 ID가 고유하고 연결 대상이 존재한다.
- Source node와 decision ID가 기존 통합 graph·검토 기록에 존재한다.
- 모든 장면은 시연용이다. 자동 timer·전화·정보 전송·이동 허용 동작이 없다.
- SC01에서 이동 가능과 운전자·경로 미확인이 함께 유지된다. 통화 연결 후에도 구호 접수는 미확인이다.
- SC03에서 응답 없음 이후 부상·의식은 미확인이다. 응답 가능한 button은 남아 있다.
- SC05에서 구호·차량 지원·보험 상태가 독립적이다. 시연 일시 중단·재개로 요청이 추가되거나 상태가 초기화되지 않는다.
- 잘못된 URL은 기본 scenario·초기 장면으로 복구한다. Scenario 변경 시 이전 장면을 잘못 재사용하지 않는다.
- Focus, reduced motion, TTS 실패 fallback, 좁은 browser의 검토 control을 확인한다.

실행: `node --test specs/emergency-experience/manifest.test.mjs`, `cd prototype/web && npm run check && npm run test:ui`.

## 실제 browser 확인

모든 장면을 1440 × 810 원래 크기와 laptop 전체 보기에서 확인한다. 핵심 label·button·미확인·기관 상태가 잘리지 않아야 한다. 375px 검토 UI와 reduced motion도 확인한다. Screenshot은 구조와 표시의 증거이며 이해도 검증 결과가 아니다.

## 사용자 이해도 평가 — 아직 미실시

동료에게 설명을 먼저 제공하지 않고 같은 scenario를 제시한다. 첫 실험은 3초 노출 후 화면을 가리는 방식으로 제안한다. 3초는 이 프로젝트의 탐색 조건이며 안전 기준이나 합격 시간으로 해석하지 않는다. 후보 순서를 교차하고 이전 화면을 본 경험을 기록한다.

| 질문 / 과제 | 기록 |
| --- | --- |
| 지금 어떤 상황인가? | 답변 원문, 핵심 상태의 일치 여부 |
| 다음에 무엇을 해야 하는가? | 답변 원문, 첫 선택, 선택까지 걸린 시간 |
| 아직 모르는 것은 무엇인가? | 미확인 인식 여부 |
| 차량을 움직여도 되는가? | 이동 가능과 이동 허용의 혼동 |
| 연락이 연결되면 접수된 것인가? | 연결·전송·접수의 혼동 |
| 어떤 지원이 아직 확인되지 않았는가? | 기관별 상태 혼동 |

중대한 오해가 한 번이라도 관찰되면 해당 표현을 다시 검토한다. 소수 평가에서 오해가 없었다고 실제 긴급 상황의 안전성을 입증하지 않는다. 디자인 선호도는 이해도 결과와 별도로 기록한다.

## 결과 기록 형식

`날짜 / 익명 참여자 ID / scenario / 후보·노출 순서 / 노출 조건 / 답변 원문 / 첫 선택 / 시간 / 오해 / 수정할 표현`을 기록한다. 실험 참가자나 성공률을 만들어 넣지 않는다.

## 이후 native 확인

선택된 표현을 Kotlin + Compose로 구현한 뒤 실제 화면 크기·주야간·시야각·font scale·touch·차량 audio focus·기관 연계를 각각 검증한다. 현재 spec만으로 Pleos 규정 준수나 안전 안내 적합성을 선언하지 않는다.
